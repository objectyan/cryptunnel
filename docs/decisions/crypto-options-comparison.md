- 触发问题: 「加密解密的公钥私钥是不是要可配置呀」
- 相关: [ADR-0003 加密算法可插拔](adr/0003-pluggable-tunnel-cipher.md)、约束 C-01

---

## 0. 先澄清一个概念

**当前没有公钥私钥。** 本项目用的是**对称加密**，两套预共享密钥：

| 密钥 | 作用 |
|------|------|
| `aes-key` | 派生 AES 密钥（`SHA-256("AES:"+k)`）+ HMAC 密钥（`SHA-256("HMAC:"+k)`），加密**数据流** |
| `auth-key` | 作为 AUTH 报文的明文内容参与**身份认证**，不参与密钥派生 |

两者均已在 yml 中 **per-target 可配置**。所以「密钥能不能配」的答案是：**早就能配**。

真正值得讨论的是：要不要引入**非对称加密**，以及**换不换对称算法**。

---

## 1. 关键约束：JDK 8 算法可用性

`cryptunnel-core` 编译目标为 **1.8**，且宿主 sunrise 运行在 **JDK 8**，因此算法必须在 JDK 8 的 JCE 中可用。

| 算法 | JDK 8 可用 | 说明 |
|------|-----------|------|
| AES-256-CBC（现状） | 是 | — |
| **AES-256-GCM** | **是** | JEP 115：JDK 8 的 SunJCE 已实现 `AES/GCM/NoPadding` |
| ChaCha20-Poly1305 | **否** | JEP 329，JDK **11+** 才引入 |
| **SM4（国密）** | **否** | SunJCE 算法列表无 SM4，任何 JDK 版本都需 BouncyCastle |

> 注：编译目标 1.8 但宿主若运行 JDK 11+，ChaCha20 可用。但按 sunrise 的 JDK 8 现状，应保守按 JDK 8 判断。

## 4. 各方案详述

### 方案 0：维持现状

保持 AES-256-CBC + HMAC-SHA256，密钥 per-target 配置。

- 优点：零成本、零风险、老客户端兼容完好
- 缺点：密钥分发靠人工（每新增一个使用者都要传递 `aes-key`）；静态密钥无前向安全
- 说明：ADR-0003 的 SPI 已就位，**加新算法的成本已大幅降低**，但「成本降低」不等于「现在就该加」

### 方案 1：换 AES-256-GCM

用 AEAD 模式替代 CBC + 外部 HMAC，认证与加密合一。

- 优点：JDK 8 原生支持，**无需额外依赖**；消除 CBC + HMAC 组合的误用风险；更安全现代
- 缺点：**破坏老客户端兼容**（线级格式变化）；GCM 的 nonce 复用风险需严格管理（本项目每帧随机 IV，风险可控）
- 适用：愿意接受一次破坏性升级，换取更干净的密码学构造

### 方案 2：换 SM4（国密）

- 优点：满足国密/合规要求（部分单位强制）
- 缺点：JDK 8 **原生不支持**，必须引入 BouncyCastle（core 目前零外部依赖，这条会打破）；无硬件加速，性能低于 AES；同样破坏老客户端兼容
- 适用：有明确合规要求时

### 方案 3：混合加密（非对称密钥交换）

```
1. 服务端持有密钥对（私钥留存，公钥可公开分发）
2. 客户端生成随机会话密钥
3. 客户端用【服务端公钥】加密会话密钥 → 发送
4. 服务端用【私钥】解密，得到会话密钥
5. 之后的数据流用会话密钥做对称加密
```

- 优点：**唯一能解决密钥分发问题的方案**——客户端只需持有不怕泄露的公钥；会话密钥每次连接临时生成，可获前向安全
- 缺点：
  - 破坏老客户端兼容（协议必然变化）
  - 服务端需管理密钥对（生成/存储/轮换）
  - **多一次握手往返**——对当前未解决的「重连慢 10 秒」是雪上加霜
  - 三端都要改
- 适用：确实存在「给同事发密钥很麻烦/不安全」的痛点

### 方案 4：全非对称（对照，不可行）

| | AES-256-CBC | RSA-2048 |
|---|---|---|
| 吞吐 | ~1-2 GB/s | ~0.1 MB/s |
| 单次上限 | 无 | 245 字节 |

相差数千倍，且单次有 245 字节上限。**业界无例外**——TLS 也是握手用非对称、数据用对称。仅列为对照，证明「直接加密数据流」不是选项。

## 5. 一个必须说清楚的前提

以上方案的**共同目标假设**是「换算法有助于过防火墙」。但这一点**尚未验证**：

| 防火墙类型 | 换算法有用吗 |
|-----------|-------------|
| 封端口 | 无用（C-02 已通过复用宿主端口解决） |
| 只放行 HTTP/HTTPS 协议 | **无用**——需要流量伪装，不是换加密算法 |
| DPI 识别「加密隧道特征」 | **可能有用**（改变特征），但不保证，需实测 |

**在不知道防火墙拦什么之前加算法，很可能加错。** 这是把这些方案列为「待决策」而非直接实施的核心原因。

## 6. 初步推荐

**推荐：方案 0（维持现状），暂不动。**

理由：

1. **10 秒问题未结案**——正在查「断了重连慢 10 秒」，此时在连接建立路径上叠加改动会互相干扰
2. **过墙效果未知**——换算法未必解决问题，需先确认防火墙类型
3. **老客户端零改动是硬承诺**——方案 1/2/3 都会破坏它，需要足够强的理由才值得
4. **架构灵活性已经拿到**——ADR-0003 的 SPI 就位后，将来任何时刻加算法的成本都已降低，**不急于现在**

各方案触发条件：

| 如果出现这个情况 | 选这个方案 |
|-----------------|-----------|
| 确认防火墙是 DPI 特征识别，且 AES 特征被拦 | 1（AES-GCM）或 2（若需国密） |
| 有明确国密合规要求 | 2 |
| 密钥分发成为真实痛点（人员频繁变动、密钥传递有泄露风险） | 3（且建议等 10 秒问题解决后） |
| 防火墙只放行 HTTPS 协议 | **以上都不是**——需要流量伪装，另开议题 |

## 8. 决策结果（2026-09-09）

### 用户回答

1. 防火墙拦的是**请求内容里的数据**——不加密、含脚本特征就被拦截
2. 当前**仅 1 人使用**，后期会开放给多人
3. 密钥多人分发**现阶段可行**

### 决策

**采用方案 0：维持现状**（AES-256-CBC + HMAC-SHA256，预共享密钥）。
方案 1 / 2 排除，方案 3 列为**条件触发**而非现在实施。

### 理由

1. **防火墙是「明文特征匹配」，换算法无额外收益。**
   它拦的是内容里的脚本特征，而非某种加密算法的指纹。任何有效加密都能消除明文特征——现状已满足 C-01。
   因此**方案 1（AES-GCM）与方案 2（SM4）被排除**：它们改变的是「用哪种算法」，而需要消除的是「明文」，属于打错靶子。

2. **密钥分发当前不是痛点。**
   使用者 1 人，且用户明确表示多人分发可行。方案 3（混合加密）的唯一真实价值是解决密钥分发，当前无此需求。

3. **方案 3 会恶化未结案的性能问题。**
   它需要在连接建立路径上多一次密钥交换往返，而「重连慢 10 秒」尚未定位。

### 触发条件（何时重新评估）

| 触发事件 | 动作 |
|---------|------|
| 使用者增长到密钥分发成为负担（人员频繁变动、传递有泄露风险） | 评估方案 3 |
| 有明确国密合规要求 | 评估方案 2（需先接受引入 BouncyCastle） |
| 确认防火墙改为识别「加密算法特征」而非明文特征 | 重新评估方案 1 / 2 |

### ⚠ 一个必须澄清的误解

**ADR-0003 的 `TunnelCipher` SPI 解决不了「引入混合加密」。**

| | SPI 能帮上忙吗 | 原因 |
|---|---|---|
| 换对称算法（GCM / SM4） | **能** | 新增一个实现类 + 注册即可 |
| 引入混合加密 | **不能** | 它是**协议变更**（多一次密钥交换握手），不是换算法 |

若将来真要上方案 3，工作量与 SPI 是否就位**基本无关**。

### 已知技术债

当前 AUTH 报文格式为 `AUTH:{authKey}:{ts}:{nonce}[:{targetId}]`，**没有协议版本号字段**。
将来若要引入密钥交换或任何协议扩展，都必须做一次破坏性升级。

- **当前决策：不加。** 老客户端零改动优先。
- 待将来确实需要时，一次性引入版本号 + 能力协商，把破坏性升级收敛到一次。
