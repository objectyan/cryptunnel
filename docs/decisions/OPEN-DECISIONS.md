| 编号 | 约束 | 来源 | 影响面 |

## 约束 C-02 的直接推论

1. **方案 C（把 JDBC 隧道降级为 orbien 的一条 TCP 代理规则）在 ADR-0002 中已被否决，C-02 使其否决理由从"安全风险"升级为"物理不可行"**——orbien server 是独立进程，默认监听 `0.0.0.0:9527`，与"不能开新端口"直接冲突。
2. 本项目 starter 内嵌形态**恰好满足 C-02**：它挂在宿主应用的 Servlet 容器上，隧道端点 `/ws-cryptunnel` 与业务接口共用同一个 HTTP 端口与同一个 TLS 证书，不新增监听端口。
3. C-02 使得 orbien 的「HTTP/HTTPS 反向代理复用 80/443」经验**不可直接移植**——orbien 是用独立 server 复用 80/443，而本约束要求是复用**宿主应用已有**的端口。二者形态不同。
4. C-02 隐含：若宿主站点走 HTTPS，隧道自动升级为 WSS，无需额外证书（复用宿主 TLS）。这是内嵌形态相对于独立穿透服务端的一个实质优势。

## 加密可插拔的协商悖论（C-01 落地的核心难点）

**目标**：能更换加密算法以规避 DPI 特征识别（C-01）。

**悖论**：

| 方案 | 做法 | 问题 |
|------|------|------|
| A. 运行时协商 | 握手阶段明文携带算法标识，双方协商 | **报文里出现"可换算法隧道"的明文特征，等于给 DPI 递名片**，与 C-01 目标直接冲突 |
| B. 配置期约定 | 两端各自配置成同一算法，报文不含标识 | 换算法须同时改两端配置并重启，"可插拔"退化为「部署期可选」，运维成本高 |
| **C. 无标识试解** | 报文不含算法标识；服务端按已注册 cipher 列表**逐个试解**，HMAC 校验通过者即为所用算法 | O(N) 试解开销（N 通常个位数）；cipher 列表顺序影响性能 |

**关键洞察**：方案 C 与现有 `TargetDiscovery` **同构**——当前 AUTH 报文本就是加密的，服务端已用「逐 target 试解 + HMAC 校验定位」确定目标。因此把 cipher 定位复用同一模式，**架构上几乎零新增概念**，是三个方案中唯一不破坏 C-01 且支持两端独立演进的。

**待用户拍板**：A（灵活性最高但暴露特征）/ B（最简单但运维重）/ C（推荐，与现有架构同构）。

**兼容性红线**：无论选哪个方案，默认 cipher 实现必须**字节级等价于现有 `AES-256-CBC + HMAC-SHA256 + Base64(IV‖HMAC‖密文)`**，否则破坏「老客户端零改动」承诺。

## 性能痛点：首次连接慢（2026-09-09 用户反馈，待诊断）

**症状**：第一次连接要等很久。

**该症状修正了「动机 = 开源工程化」的结论**——存在真实性能痛点，借鉴重点需重新评估（不再只是文档/CI 层面）。

### 候选根因（按可能性排序）

| # | 假设 | 是否隧道问题 | 说明 |
|---|------|-------------|------|
| 1 | DBeaver 首次连接**元数据加载**（information_schema 查询风暴） | **否** | JDBC 特性。首次连某个库要拉库/表/列/索引等元数据，产生大量往返；连过一次后 DBeaver 本地缓存命中，故"第一次慢、后续快" |
| 2 | DNS / TCP / TLS 冷启动 | 部分 | 首次无 DNS 缓存、无连接复用 |
| 3 | JVM 预热 / 类加载 | 否 | 客户端或服务端首次调用 |
| 4 | `chunk=4096` 帧数偏多 | 是 | 受 ADR-0001 的 8192 单帧上限约束 |
| 5 | `TargetDiscovery` 试解 O(N) | 是 | 但微秒级，可能性最低 |

### 诊断进展（2026-09-09 用户补充）

用户补充症状：**「不断的情况下可以，断了就慢（约 10 秒）」**。

→ 慢发生在**连接建立阶段**，稳态传输正常。**再次排除**压缩 / 多路复用 / 去 Base64（它们只影响吞吐，而稳态是好的）。

**代码证据链**：

1. `DefaultTcpTunnel.open()`：每次 `new Socket()` + `s.connect(...)`，**无连接池**
2. `DefaultAuthenticatedSessionManager:68`：每次 AUTH 通过即 `tunnel.open(target)` 新建一条 MySQL 连接
3. 故**每次重连 = 一次完整 MySQL 建连**（TCP 三次握手 + MySQL 握手 + 认证 + 服务端反向 DNS）

### 诊断进展 v2（2026-09-09 用户截图反馈）

**已排除**：

| 原假设 | 验证结果 |
|--------|---------|
| MySQL 服务端反向 DNS 解析 | 用户截图 `SHOW VARIABLES LIKE 'skip_name_resolve'` = **ON**。**排除** |
| `MySqlConnection` 构造中做 MySQL 握手 | 代码确认构造**只取 InputStream/OutputStream，不读握手包、不发 login request**（项目是字节流透传，握手由客户端 JDBC 驱动发起） |

**新发现（强嫌疑）**：

| 线索 | 数值 | 含义 |
|------|------|------|
| `CryptunnelProperties.connectTimeout` 默认值 | **10000ms** | 服务端到 MySQL 的 socket connect 超时配置为 10 秒 |
| 用户实测「断了重连」耗时 | **~10 秒** | **数字巧合**——强烈怀疑 connect 在 10 秒上下完成（若超过则抛 `SocketTimeoutException` 断开） |

### 推论

10 秒几乎确定花在 **`s.connect(10.6.10.22, 3306, 10000)` 这一步**，即**服务端到 MySQL 的 TCP 三次握手 + 内网路由/防火墙首包检测**。字节流透传架构下，服务端只建 TCP 连接、MySQL 协议握手由客户端 JDBC 驱动发起，**隧道代码本身在这一步没有可优化空间**。

**下一步验证（零成本、30 秒出结果）**：在**服务端机器**上直连 MySQL 测建连耗时：

```bash
time mysql -h 10.6.10.22 -u <账号> -p -e "SELECT 1"
```

- 直连 < 1 秒 → 服务端→MySQL 网络正常，问题在服务端机器自身（连接跟踪 / JVM / conntrack）
- 直连 ~10 秒 → **网络层问题**（内网防火墙对每个新 TCP 连接做深度检测、ARP 缓存失效、conntrack 表满等），与本项目代码无关，修法在基础设施层

### 诊断进展 v3（用户无服务端机器 shell 权限，2026-09-09）

用户反馈：**无法在服务端机器执行 `time mysql ...`**（无权限）。原验证方案作废，改用以下两项。

#### 方案一：纯配置二分实验（零代码，推荐）

`connectTimeout` 是可配置项。把 target 的 `connect-timeout` 从默认 **10000** 改为 **3000**，重启宿主应用后观察：

```yaml
cryptunnel:
  targets:
    <name>:
      connect-timeout: 3000    # 原为默认 10000
```

| 观察结果 | 结论 |
|---------|------|
| 连接**快速失败**（约 3 秒抛 `SocketTimeoutException`） | **证实**慢就在 `s.connect()` 这一步（TCP 建连 > 3 秒）→ 根因在网络/基础设施层，与本项目代码无关 |
| 行为**不变**（仍约 10 秒后连上） | 慢**不在** TCP connect，需转向 MySQL 握手或隧道其他环节 |

原理：若真卡在 TCP 建连，缩小超时阈值会把「等 10 秒后成功」变成「3 秒即失败」，是一次干净的二分。

> 注意：target 白名单为启动期加载，改完**必须重启宿主应用**才生效（已知限制）。

#### 方案二：纯 SQL 诊断（有 MySQL 访问权限即可，无需机器 shell）

```sql
SHOW VARIABLES LIKE 'connect_timeout';   -- MySQL 服务端默认也是 10 秒，注意数字巧合
SHOW STATUS LIKE 'Aborted_connects';     -- 重连后是否 +1，是则连接建立确有问题
SHOW STATUS LIKE 'Threads_connected';    -- 当前连接数，接近 max_connections 则新连接会卡
SHOW VARIABLES LIKE 'thread_cache_size'; -- 为 0 则每次新连接都要新建线程
SHOW VARIABLES LIKE 'max_connections';
```

#### 待用户反馈

- 方案一的观察结果（快速失败 / 行为不变）
- 方案二中 `connect_timeout` 与 `Aborted_connects` 的取值

### 诊断进展 v4（用户回填 MySQL 变量，2026-09-09）

| 变量 | 实测值 | 判断 |
|------|--------|------|
| `connect_timeout` | **10** | MySQL 服务端等待客户端认证包的超时（默认 10 秒） |
| `Aborted_connects` | **414** | 偏高，**待确认增长率** |
| `Threads_connected` | 29 | 29 / 3000，**排除**连接数打满 |
| `thread_cache_size` | 38 | 29 < 38，有缓存可用，**排除**线程创建慢 |
| `max_connections` | 3000 | 远未满 |

**已排除**：连接数打满、线程缓存不足导致的建连慢。

**核心假设（新）**：`connect_timeout = 10` 与用户实测「约 10 秒」**数值一致**。结合 `Aborted_connects = 414` 偏高，最可能的解释是——

> 每次重连时，MySQL 建连后**等待客户端认证包等满 `connect_timeout`(10s) 仍未收到 → 主动断开 → `Aborted_connects` +1**；客户端随后重试并成功。用户感知的「10 秒」正是 MySQL 的这个等待窗口。

**⚠ 关键区分**：此处的 10 秒是 **MySQL 服务端的 `connect_timeout`**，**不是**本项目 `CryptunnelProperties.connectTimeout = 10000`。两者数值巧合，含义完全不同：

| | 本项目 `connectTimeout` | MySQL `connect_timeout` |
|---|---|---|
| 作用对象 | 服务端 → MySQL 的 **TCP 三次握手** | MySQL 等待**客户端认证包** |
| 超时后果 | `SocketTimeoutException` | MySQL 主动断开 + `Aborted_connects` +1 |

因此**修改本项目的 `connectTimeout` 对本症状无效**（方案一的二分实验仍可用于排除 TCP connect，但即使排除也不解决本问题）。

**关键待验证**：`Aborted_connects` 增长率测试

1. 记录当前值 `414`
2. 断开 DBeaver → 重新连接一次
3. 再次读取该值：
   - **变为 415** → 证实「每次重连都在 MySQL 侧失败一次」，核心假设成立
   - **不变** → `414` 是历史遗留，与本问题无关，需另找方向

### 附带发现：代码缺陷（与性能无关，独立登记）

| 缺陷 | 位置 | 说明 |
|------|------|------|
| **自动重连是死配置** | .NET 客户端 `BuiltinDefaults.AutoReconnect` / `ReconnectDelayMs`（3000） | 这两个配置项仅在 `BuiltinDefaults` / `RawConfig` / `ProjectConfig` / `ConfigLoader` / `ConfigWriter` / `Runtime` 之间流转，**全项目无任何业务代码消费**。即「自动重连」从未实现，配置写了不生效 |
| MySQL 连接无池化 | `DefaultTcpTunnel.open()` | 每会话一连接。**这是正确的安全设计**（避免会话混淆），不建议为性能改为连接池 |
