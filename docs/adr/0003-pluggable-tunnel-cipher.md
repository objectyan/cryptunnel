# ADR-0003: 加密算法可插拔（TunnelCipher SPI）

- 状态: 已接受
- 日期: 2026-09-09
- 相关组件: `cryptunnel-core`、`cryptunnel-spring-boot-starter`
- 相关约束: C-01（数据流必须加密，否则过不了防火墙）
- 相关 ADR: ADR-0002（与 orbien 的关系：只借鉴设计，不做协议兼容）

## 背景

C-01 要求数据流加密以通过防火墙。当前实现为固定的
`AES-256-CBC + HMAC-SHA256`，硬编码在 `AesUtil` 静态方法里。

若固定算法的特征被 DPI 识别，需要有更换算法的能力，而不是改核心代码。

同时，ADR-0002 已确立「只借鉴设计，不做协议兼容」，因此本决策**不涉及**与任何第三方项目的互操作。

## 决策

引入 `TunnelCipher` SPI，使加密算法可插拔。采用**配置期约定**（方案 B）：

1. **报文内不含算法标识。** 线上载荷一个字节的算法标识都不放——携带明文标识等于向 DPI 宣告「这是可换算法的隧道」，与 C-01 目标直接冲突。
2. **两端各自配置成同一算法。** 客户端与服务端在配置文件中指定 `cipher`，约定一致。
3. **服务端限死单 cipher。** 服务端同一时刻只允许启用一个 cipher；配置多个直接 fail-fast 启动失败。

### 接口形状

```java
public interface TunnelCipher {
    /** 算法标识：仅用于本地配置匹配与日志，绝不进报文 */
    String id();

    /** 明文 -> 线上载荷（算法自行决定格式，含 IV / 校验值 / 编码） */
    String seal(byte[] plaintext, String rawKey);

    /** 线上载荷 -> 明文；校验失败抛 TunnelCryptoException */
    byte[] open(String payload, String rawKey);
}
```

### 关键取舍

**① `seal` 返回 `String` 而非 `byte[]`**

现有链路是 WebSocket `TextMessage` + Base64。若返回 `byte[]`，调用方需自行 Base64，等于把「编码格式」从算法中剥离，将来想换成非 Base64 编码就动不了。让算法自己管编码，换算法时才真正自由。

按 C-01（过防火墙），保持文本载荷反而是我们要的，因此该取舍当前无实际代价。

**② 传入 `rawKey` 而非 `SecretKeySpec`**

`SecretKeySpec` 绑定 JCE 体系。传原始密钥字符串，由各算法自行决定派生方式——现有 `SHA-256("AES:"+k)` / `SHA-256("HMAC:"+k)` 只是默认实现的内部细节，不是协议的一部分。

**③ `id()` 不进报文**

见决策第 1 条。`id()` 仅用于本地配置匹配与日志输出。

### 兼容性红线

默认实现 `AesCbcHmacSha256Cipher` **必须字节级等价于现有实现**：

- 载荷格式：`Base64( IV[16] || HMAC[32] || AES/CBC/PKCS5Padding 密文 )`
- HMAC 覆盖范围：`IV || 密文`
- 密钥派生：`SHA-256("AES:" + rawKey)` / `SHA-256("HMAC:" + rawKey)`

实现上采用**直接委派**给现有 `AesUtil`，而非重新实现，从构造上杜绝偏差。已有 38 个单元测试 + 黄金向量共同锁死。

**老客户端零改动**是硬承诺：默认 cipher 走 SPI 与直接调 `AesUtil` 必须产生完全相同的字节。

### 异常处理

新增 `TunnelCryptoException extends RuntimeException`（非受检）。

兼容性已确认：`TargetDiscovery.discover()` 使用 `catch (Exception e)` 兜底并继续尝试下一个 target，因此异常类型变化**不影响**试解逻辑。

## 后果

### 正面

- 更换算法从「改核心代码」变为「新增实现类 + 改配置」，工程价值明确
- 默认实现委派现有 `AesUtil`，字节级等价由构造保证，老客户端零改动承诺不受影响
- 报文零标识，不给 DPI 递名片
- 服务端限死单 cipher，语义清晰、无隐藏开销、无隐式试解

### 负面 / 代价

- **不能灰度过渡**：换算法须客户端与服务端同时改配置并重启。若将来需要「服务端同时支持新旧算法」的平滑过渡，本决策需重新评估。
- **算法配错时错误信息具有误导性**：服务端解不开时只报「认证失败」，不会提示「算法不匹配」。运维排障会多绕一圈。

### 后续

若将来出现灰度需求，可放宽为「服务端允许注册多个 cipher + 无标识试解」（即 ADR 备选方案 C）。届时因 `TunnelCipher` 接口已就位，扩展成本可控。

## 备选方案（已否决）

| 方案 | 做法 | 否决理由 |
|------|------|---------|
| **A. 运行时协商** | 握手时明文携带算法标识，双方协商 | 报文出现「可换算法隧道」的明文特征，等于给 DPI 递名片，与 C-01 直接冲突 |
| **C. 无标识试解** | 报文不含标识，服务端按已注册 cipher 逐个试解 | 与现有 `TargetDiscovery` 同构（架构上优雅），但用户明确选择 B，理由是不接受试解开销 |

> 补充说明：试解实际只在连接建立的 AUTH 阶段发生一次，认证通过后 cipher 即被会话绑定，数据通道不再试解；单次 AES 解密 + HMAC 校验为微秒级，相对毫秒级的握手开销可忽略。方案 C 的开销在实测中并不构成瓶颈。本 ADR 采纳 B 是基于用户对「简单可预测」的偏好，而非 C 存在性能问题。

## 落地记录（2026-09-09 补充）

SPI 就位后，本决策的「留口子」阶段已结束——**三种算法已实现并三端落地**。
使用与切换方式见 [隧道加密算法：现状与扩展指南](../replacing-the-cipher.md)。

| 算法标识 | 帧结构 | 服务端 | 老 Java 客户端 | .NET 客户端 |
|---|---|---|---|---|
| `aes-256-cbc-hmac-sha256`（默认） | `Base64(IV[16] \|\| HMAC[32] \|\| 密文)` | ✅ | ✅ | ✅ |
| `aes-256-gcm` | `Base64(nonce[12] \|\| 密文 \|\| tag[16])` | ✅ | ✅ | ✅ |
| `sm4` / `sm4-cbc-hmac-sha256` | 同默认算法 | ✅ 需 bcprov | ✅ 内置 bcprov | ✅ 自实现 |

### 实施中新增的三条约定

**① `TunnelCipher` 增加 `aliases()` 默认方法**

`sm4-cbc-hmac-sha256` 这类完整标识在 yml 里太长，允许实现声明短名（`sm4`）。
别名只用于配置匹配，同样不进报文，不违反决策第 1 条。

**② 第三方依赖走条件注册，不是硬依赖**

SM4 需要 BouncyCastle，但 core 必须对不用 SM4 的宿主保持零依赖。
做法：BC 在 core 中声明为 `optional`，`TunnelCiphers` 用 `Class.forName` 探测后再反射注册。
缺依赖时**不注册**该算法，配置 `cipher: sm4` 得到「缺少依赖 org.bouncycastle:bcprov-jdk18on」
的明确报错，而不是 `NoClassDefFoundError`。

**③ 跨算法必须硬失败，这是安全属性而非实现细节**

因为报文无算法标识，两端配置不一致时**绝不能解出垃圾数据当成合法明文**。
最危险的组合是 CBC ↔ SM4：两者帧结构相同、HMAC 密钥相同，
**HMAC 校验会通过**，只能靠分组算法不同导致 PKCS7 填充非法来兜住。
这一条已被 parity 自检的六组两两互解断言锁死。

### 对「负面代价」一条的实际缓解

ADR 原文指出「算法配错时错误信息具有误导性」。客户端侧已做了部分缓解：

- 未知算法名在**加载配置阶段**即拒绝，并列出可用值（不会等到连接失败）
- 配了非默认算法时给出警告，提示同步检查服务端 `cryptunnel.cipher`

但**根本问题依然存在**：客户端无法探测服务端配了什么——报文里没这个信息。
两端都配了合法但不同的算法时，仍然只表现为认证失败。这是方案 B 的固有代价。
