## 四、几个不肯让步的地方

1. **帧上限硬断言，不靠服务端配置。**
   `MaxFramePayloadChars = 8192` 与 `ChunkSize` **分离定义**，禁止 `ChunkSize * 2` 这类隐式耦合；断言放在唯一发送入口。
   PKCS7 膨胀实算：`ceil((48+pad16(n))/3)*4 <= 8192` → n=6095 恰好合法，**n=6096 是第一个越界值**（6096 是 16 整数倍，PKCS7 会额外补满一整块，跨度比直觉大）。ADR-0001 明确否决过「把 buffer 调到刚好塞得下」的魔数做法，这里不重犯。

2. **跨算法必须硬失败。**
   `aes-256-cbc-hmac-sha256` 与 `sm4-cbc-hmac-sha256` 帧结构逐字节相同（都是 112 B）且共享同一 HMAC 密钥 —— 算错算法时 **HMAC 会通过**，只有 PKCS7 去填充失败能拦住。所以绝不能吞异常、绝不能泄漏垃圾明文。

3. **`ExposedToNetwork` 是拒启，不是告警后继续。**
   本地端口是一个**无需任何认证**的 MySQL 入口，一旦绑到 0.0.0.0，同网络内任何人都能直接打内网库。这条不给「我知道风险，继续」的选项。

4. **HTTP 降级保留，但诚实标注边界。**
   `/tunnel` 是严格请求-响应配对，服务端无法主动推送；`in.available()` 有竞态；`maxWait=30000` 让 POST 最坏挂 30 秒。这三条**客户端一条都修不了**（账挂在 ADR-0001:37）。因此不默认关闭、也不假装完整：强制 `Status = Degraded` + 明确告警。
   > 宁要一个诚实标注边界的功能，也不要一个假装完整的。

5. **认证真的去 `ReceiveAsync`，不是 `Delay` 混过去。**
   服务端认证成功**不发 ACK**，只有失败时才带 close reason。若只 `Delay` 不 `Receive`，那张九条映射表就白做了 —— 用户永远只能看到「连不上」。

6. **WS 分片必须重组。**
   漏掉 `EndOfMessage == false` 的症状是「小结果集正常、大结果集随机失败」，而且失败形式是 Base64 截断抛出的 `CryptographicException` —— 和密钥配错**长得一模一样**，会把人往完全错误的方向带。
