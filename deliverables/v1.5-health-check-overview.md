# v1.5 客户端健康检查（探活）—— 交付概览

> Task #36 收口。服务端零改动。2026-09-10。

## 一句话

把「点了没反应还骗人」的假指示灯，换成一条真实跑完 **网络 → 认证 → MySQL** 三层的探活链路，
支持手动触发与周期性自动运行，**服务端不需要改一行代码**。


## 一、先修掉的既有缺陷：原「测试」按钮是假指示灯

`AppController.TestConnection`（原 384-403 行，本次**已删除**）只用 `TcpClient`
连**本进程自己**的监听端口。

**第一层缺陷 —— 它测不出任何东西。**
判定结果等价于界面上「监听中」三个字。以下四种真实故障，它**全部报 ✔**：

| 真实故障 | 原「测试」的结论 |
|---------|----------------|
| authKey 配错 | ✔ 连通 |
| cipher 与服务端不一致 | ✔ 连通 |
| 服务端宕机 | ✔ 连通 |
| 服务端连不上 MySQL | ✔ 连通 |

**第二层缺陷 —— 它有隐蔽副作用。**
连自己端口会被 `AcceptLoop` 收下，于是日志打出「DBeaver 已连接，建立隧道…」，
`TryWebSocketMode` **真的去连服务端、真的完成加密认证、服务端真的开了一条 MySQL 连接**。
而测试用的 `using var client` 此时早已 Dispose，写握手包失败，再打一句「写入握手包失败」。

净效果：点一次「测试」= 服务端多一条 MySQL 连接建了又断 + `Connections` 统计 +1
+ 两条误导日志，**而真正探到的结论全被丢弃**。

> 一个在所有真实故障下都亮绿灯的指示灯，比没有指示灯更危险 ——
> 它会让用户排除掉本该首先怀疑的方向。


## 二、探活能验到什么（以及验不到什么）

| 层 | 能否探到 | 说明 |
|----|---------|------|
| TCP / TLS 可达 | ✅ | 含 WAF 是否放行 |
| WebSocket 握手 | ✅ | |
| 加密认证 | ✅ | 一次覆盖 **authKey + aesKey + cipher** 三项是否与服务端一致 |
| **服务端 → MySQL 可达** | ✅ **白拿** | 见下 |
| **MySQL 版本号** | ✅ **白拿** | 解握手包得到 |
| 分层 RTT | ✅ | 各层独立计时 |
| MySQL 账号密码是否正确 | ❌ | 账密由用户在 DBeaver 里填，客户端根本没有 |

### 为什么后两项是白拿的

服务端认证通过后**不发任何 ACK**，而是直接连 MySQL 并把 MySQL 的握手初始化包
原样推给客户端（`CryptunnelWebSocketHandler:138-141`）。

> **收到首帧 = 认证已通过，且服务端已经连上了 MySQL。**

这条推论让「数据库可达」成为探活白送的一层，无需服务端做任何配合。

### 它带来的一个必须接受的代价

认证成功的时刻在线路上**没有任何可观测信号**，因此认证层与数据库层
在物理上就无法分开计时。设计决定是：**认证层耗时记 0，等待时间全部计入数据库层**，
并把理由写进代码注释 —— 宁可让一层的耗时偏大，也不能凭空编一个认证耗时，
那个数字会被用户拿去做性能判断。

### 能力上限是架构决定的

再深一层（验证 MySQL 账号密码）需要发送 MySQL 登录包，而账密在 DBeaver 里，
客户端从来就没有。**上限就到握手包**，这不是实现偷懒。

## 四、关键设计决策

1. **Skipped ≠ Pass ≠ Fail，三态。**
   前一层失败后，后续层没跑过。显示成「通过」是撒谎，显示成「失败」会把用户
   引向一个其实没被验证过的方向。视觉上用 `○` 置灰 + 耗时显示 `—`
   —— 显示 `0ms` 会让人以为「跑了而且很快」。

2. **只在状态跳变时打日志。**
   每 5 分钟一行「健康检查通过」= 一天 288 行噪声，会把真正的错误淹没。
   持续健康时**完全静默**，只在 健康→故障 / 故障→恢复 两个跳变点发声。

3. **`NextRun` 从「本次结束」而非「本次开始」计时。**
   否则探活耗时 10 秒时实际间隔缩水，慢链路上会越跑越密 ——
   而那正是本功能最该避免的后果。

4. **`intervalSec < 30` 硬拒绝，不夹到下限。**
   悄悄夹一下会让配置文件里的数字与实际行为不一致，下次排查又多一层误导。

5. **`health.enabled` 默认 false（opt-in）。**
   每次探活真实占用服务端一个 `maxConnections` 名额，也会让 MySQL 的
   `Connections` 计数持续增长。链路稳定时这笔开销买不到什么。

6. **配置回写必须保住界面未覆盖的字段。**
   编辑器保存时构造全新 `ProjectFile`，界面上没有的字段一律 null ——
   「改了个端口号，顺手把 health 段抹掉了」且无任何提示，是最隐蔽的一类数据丢失。

7. **`HealthReport.StartedAt` 存本地时间而非 UTC。**
   它唯一的用途是显示给用户，而用户对照的是自己的墙上时钟。
   存 UTC 会让每个消费方都得记着转一次，漏一处就是差 8 小时的错误时间。

8. **`Stop()` 先 Dispose 调度器再停隧道。**
   反过来的话，最后一拍可能刚好排出一次探活，用户会在退出瞬间
   看到一条毫无意义的「健康检查失败」。

9. **`ApplyHealth` 只改健康属性，绝不碰 `State` / `Errors`。**
   探活走的是一条与业务隧道完全独立的连接，它失败不等于隧道断了
   （可能只是服务端连接数暂时打满）。让它去改隧道状态会制造出
   与真实数据流相矛盾的显示。

### MySQL 协议的两个坑（已用断言钉住）

- **ERR 包的 SQLState 段（`'#'` + 5 字节）只在客户端声明 CLIENT_PROTOCOL_41 时才出现，
  握手阶段通常没有。** 必须按首字节 `'#'` 动态判断；无条件跳 6 字节会把错误文本
  的前 6 个字符吃掉，且不会报任何错。
- **ERR 包必须与「连不上」严格区分。** 1130 Host not allowed / 1040 Too many connections /
  1045 Access denied —— 这些说明服务端→MySQL 的网络是通的，是 MySQL 主动拒绝，
  排查方向与「网络不通」**完全相反**。

### 定点变异（3 次，证明断言不是摆设）

| # | 注入的缺陷 | 结果 | 是否误伤无关项 |
|---|-----------|------|--------------|
| 1 | ERR 包 SQLState 判断去掉，改成无条件跳 6 字节 | **128 / 2 失败** | 否，命中的正是那 2 条 SQLState 断言 |
| 2 | 错误码小端 → 大端 | **124 / 6 失败** | 否，全是 ERR 包相关 |
| 3 | `IsHealthy` 把 Skipped 当作通过 | **129 / 1 失败** | 否，只命中「Pass+Pass+Skipped 也不算健康」 |

三次变异均**只命中相关断言、不误伤无关项**，说明断言是定向的，
而不是靠一堆连锁反应蒙对。三处代码已 `grep` 复核全部还原原状，

## 六、怎么用

### 手动检查

主界面每行项目的「检查」按钮（原「测试」）→ 弹出分层报告：
逐层列出 通过/失败/未执行 + 各层耗时 + 失败层的中文排查建议 + MySQL 版本号。
底部有「复制报告」按钮（没有它，用户只能截图，而截图里的错误码无法被搜索和粘贴）。

### 周期性自动检查（默认关闭）

在 `config.d/00-defaults.yaml` 或单个项目的 yaml 里写：

```yaml
health:
  enabled: true
  intervalSec: 300
```

结果显示在主界面状态列下方（`✓ 链路正常 21:05`），
从未检查过时整行隐藏 —— 没开这功能的项目不该留一块灰色占位，
那会让人以为「检查过但结果未知」。

**建议只在排查间歇性断线时临时打开。**
